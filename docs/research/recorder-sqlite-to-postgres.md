# Recorder: SQLite to PostgreSQL with long-term statistics intact

Research for [#6](https://github.com/thaum-xyz/lancre/issues/6), 2026-11-15. Target: Home Assistant 2025.9.4, 600 MB `home-assistant_v2.db`, `purge_keep_days: 8`, PostgreSQL from CloudNativePG (CNPG). Source copy is taken online; HA restarts once, at the `db_url` switch.

Code links are pinned to the `2025.9.4` tag of `home-assistant/core` (shortened below as `core@2025.9.4`). The pgloader links point at its `main` branch as read on 2026-11-15.

## Answer

Use **procedure B**: build an empty v50 schema from HA's own models, load only `statistics_meta`, then `statistics` and `statistics_short_term`, and move the identity sequences forward. HA treats the database as new on first start and runs no data migrations. Totals for `sum` sensors carry on from the last imported short-term row. Rationale and caveats are in [Recommendation](#6-recommendation).

## 2. Procedure A: pgloader of the whole database

Every community procedure that works uses the same pattern: HA (or its models) creates the schema, pgloader loads **data only**, then the sequences are fixed by hand.

| Source | Load file / step | Outcome reported |
|---|---|---|
| Jennes, 2020-06-18 ([post 5](https://community.home-assistant.io/t/migrate-to-postgresql/2832/5)) | `with data only, drop indexes, reset sequences, truncate`. Don't let pgloader create tables, because its types differ from HA's | works |
| Imroy, 2020-07-25 ([post 6](https://community.home-assistant.io/t/migrate-to-postgresql/2832/6)) | add `set timezone to 'UTC'` | fixes shifted datetimes |
| tobixen, 2023-03 ([posts 14-15](https://community.home-assistant.io/t/migrate-to-postgresql/2832/15); [Redpill Linpro write-up](https://www.redpill-linpro.com/techblog/2023/03/21/migrating-home-assistnt-to-postgresql.html)) | `data only, drop indexes, reset sequences, truncate, batch rows = 1000` + `SET work_mem to '32 MB', maintenance_work_mem to '64 MB'`; then `pg_dump … \| grep _seq \| perl` sets every sequence to 12345678 | duplicate-key errors until the sequences were bumped |
| FlameBoy, 2023-05 ([post 16](https://community.home-assistant.io/t/migrate-to-postgresql/2832/16)) | pgloader data-only with legacy SQLite columns (`states.domain`, `events.created`) present | load fails; later "does not support double precision" errors on statistics |
| GeoffreyFrogeye, 2024-08-24, HA 2024.5.5 ([post 20](https://community.home-assistant.io/t/migrate-to-postgresql/2832/20)) | `data only, drop indexes, reset sequences, truncate, batch rows = 1000, prefetch rows = 1000`; then `setval` for every `ADD GENERATED BY DEFAULT AS IDENTITY` column in `pg_dump --schema-only` | `states_state_id_seq` was 2711 vs `max(state_id)` 132378632 before the fix |
| mschmiedel, 2024-10-04 ([post 21](https://community.home-assistant.io/t/migrate-to-postgresql/2832/21)) | without the fix, HA's startup migration hit duplicate keys in `migration_changes` and history "vanished"; fixed with per-table `setval(…, GREATEST(MAX(id), nextval(…)-1))` | works after the fix |

**Why `reset sequences` does not help.** pgloader resets only columns whose default matches `^nextval` ([pgsql-create-schema.lisp L565-580](https://github.com/dimitri/pgloader/blob/main/src/pgsql/pgsql-create-schema.lisp#L565-L580)). HA's identity columns have no such default, so pgloader skips them. That is the root cause of the duplicate keys in posts 15, 20 and 21.

### Casts

No CAST clause is needed in `data only` mode, because the target types come from HA. The SQLite source types only select the transform ([sqlite-cast-rules.lisp](https://github.com/dimitri/pgloader/blob/main/src/sources/sqlite/sqlite-cast-rules.lisp), [docs](https://pgloader.readthedocs.io/en/latest/ref/sqlite.html)). This is derived from the code; no posted run confirms it for v50.

| HA column kind | SQLite decl | pgloader transform | Into PG | Risk |
|---|---|---|---|---|
| ids | `INTEGER` | `integer-to-string` | `bigint` identity | sequence must be fixed (above) |
| `*_ts`, stats values | `FLOAT` | `float-to-string`, Lisp `princ` of a double ([transforms.lisp L299-311](https://github.com/dimitri/pgloader/blob/main/src/utils/transforms.lisp#L299-L311)) | `double precision` | none expected |
| booleans | `BOOLEAN` | none (catch-all text) | `boolean` | `0`/`1` are valid input |
| context ids | `BLOB` | `byte-vector-to-bytea` | `bytea` | none expected |
| `recorder_runs.start`, `statistics_runs.start` | `DATETIME` | `sqlite-timestamp-to-timestamp` | `timestamptz` | naive text is read in the session timezone, so `SET timezone to 'UTC'` |
| legacy columns that HA dropped from its models but SQLite kept | various | — | column missing | COPY fails (post 16). Drop them in the copy first |

### Load file for this case (target pre-created and empty)

```
LOAD DATABASE
  FROM sqlite:///work/ha-copy.db
  INTO postgresql://app:PASSWORD@HOST:5432/app
WITH data only, batch rows = 1000, prefetch rows = 1000
SET timezone to 'UTC', work_mem to '32 MB', maintenance_work_mem to '64 MB';
```

`truncate` is left out because the target is empty. Two things are unconfirmed: whether pgloader orders the tables so that the FK constraints (`states → state_attributes/states_meta/states`, `events → event_data/event_types`) hold during COPY, and how `data only` combines with `drop indexes`. The pgloader docs don't say ([sqlite ref](https://pgloader.readthedocs.io/en/latest/ref/sqlite.html)). `disable triggers` sidesteps FK checks, but the docs warn it "can leave foreign key constraints invalid", and it needs superuser.

### Sequence fix (both procedures)

For an identity column, `pg_get_serial_sequence` returns the internal sequence ([PG docs](https://www.postgresql.org/docs/current/functions-info.html)).

```sql
DO $$
DECLARE r record;
BEGIN
  FOR r IN SELECT table_name, column_name FROM information_schema.columns
           WHERE table_schema = 'public' AND is_identity = 'YES'
  LOOP
    EXECUTE format(
      'SELECT setval(pg_get_serial_sequence(%L, %L), COALESCE((SELECT max(%I) FROM %I), 0) + 1, false)',
      r.table_name, r.column_name, r.column_name, r.table_name);
  END LOOP;
END $$;
```

## 3. Procedure B: fresh schema plus the statistics tables

No primary or community source publishes this exact procedure. The steps follow from the code above. ha-db-universal-migrator uses the same schema-creation method ([README](https://github.com/alexdelprete/ha-db-universal-migrator), first published 2026-09).

1. Confirm both ends run v50. On the copy: `SELECT schema_version FROM schema_changes ORDER BY change_id DESC LIMIT 1;` must return `50`.

   ```sh
   sqlite3 /work/ha-copy.db "SELECT schema_version FROM schema_changes ORDER BY change_id DESC LIMIT 1;"
   ```

2. Create the empty schema from HA's own models, with the exact `ghcr.io/home-assistant/home-assistant:2025.9.4` image, for example as a one-shot Job. This runs the same `create_all` HA runs on start. Leave `schema_changes` empty, so that at the switch HA takes the "new DB" path: it writes `SchemaChanges(50)` and a `statistics_runs` row at "now", and backfills nothing.

   ```sh
   DB_URL='postgresql://app:PASSWORD@HOST:5432/app' python3 - <<'EOF'
   import os
   from sqlalchemy import create_engine
   from homeassistant.components.recorder.db_schema import Base
   Base.metadata.create_all(create_engine(os.environ["DB_URL"]))
   EOF
   ```

3. Take the snapshot as late as possible before the switch. Either command gives a consistent copy ([backup API](https://www.sqlite.org/backup.html), [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html)).

   ```sh
   sqlite3 /config/home-assistant_v2.db ".backup /work/ha-copy.db"
   # or: sqlite3 /config/home-assistant_v2.db "VACUUM INTO '/work/ha-copy.db'"
   ```

4. Compare columns: `PRAGMA table_info(statistics);` on the copy against `\d statistics` in psql, and the same for the other two tables. In v50 the legacy `created/start/last_reset` columns are still in the model ([L714-726](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/db_schema.py#L714-L726)), so they should match.

   ```sh
   sqlite3 /work/ha-copy.db "PRAGMA table_info(statistics);"
   ```

5. Load the parent table first, then the children: two pgloader runs, so FK order is guaranteed.

   ```
   LOAD DATABASE FROM sqlite:///work/ha-copy.db INTO postgresql://app:PASSWORD@HOST:5432/app
   WITH data only SET timezone to 'UTC'
   INCLUDING ONLY TABLE NAMES LIKE 'statistics_meta';
   ```

   ```
   LOAD DATABASE FROM sqlite:///work/ha-copy.db INTO postgresql://app:PASSWORD@HOST:5432/app
   WITH data only, batch rows = 1000 SET timezone to 'UTC'
   INCLUDING ONLY TABLE NAMES LIKE 'statistics', 'statistics_short_term';
   ```

6. Run the sequence fix from §2 (only three tables are non-empty).
7. Verify (§4), set `db_url`, restart HA once.

Ids in `statistics_meta` are kept as they are, so `metadata_id` stays valid and no remapping is needed. Remapping would only be needed if HA had already written `statistics_meta` rows into the target, which step 2 avoids.

**The gap between snapshot and switch.** For `sum` sensors, the next compile starts from the latest **short-term** row's `state` and `sum` ([sensor/recorder.py L538-540, L633-645](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/sensor/recorder.py#L633-L645)). Energy used during the gap is therefore booked to the first period after the switch: the total survives, the hourly shape for the gap does not. This holds only if `statistics_short_term` is imported. Hourly rows are built from the short-term rows ([statistics.py L496-501](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/statistics.py#L496-L501)). This is read from the code, not tested.

## 4. Verification and schema mismatch

| Check | How | Expect |
|---|---|---|
| Row counts | `SELECT count(*), max(id), max(start_ts) FROM <t>` on the SQLite copy and on PG, for the three tables (all 13 for A) | equal |
| Sum continuity | `SELECT metadata_id, sum, state FROM statistics_short_term WHERE start_ts = (SELECT max(start_ts) FROM statistics_short_term)` on both | equal |
| Sequences | `SELECT last_value FROM statistics_id_seq` (name from `pg_get_serial_sequence`) | `> max(id)` |
| Encoding / version | `SHOW server_encoding; SHOW server_version;` | `UTF8`, ≥ 12 |
| Startup log: bad | `Column … does not support double precision` ([auto_repairs/schema.py L227](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/auto_repairs/schema.py#L227)), `Database is about to correct DB schema errors` ([migration.py L412](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/migration.py#L412)), `The database is about to upgrade`, `UniqueViolation`/duplicate key | absent |
| Startup log: benign | A: `Ended unfinished session (id=… from …)` for the run left open in SQLite ([util.py L583](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/util.py#L583)) | may appear |
| After the first hour | new `statistics` rows with `id > old max`, `sum` continuing; Developer tools → Statistics shows no issues; energy dashboard shows past days | yes |

HA validates the double precision of the statistics columns on PostgreSQL at every start, and repairs them live if they are wrong ([auto_repairs/schema.py L147-195](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/auto_repairs/schema.py#L147-L195), [migration.py L268-314](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/migration.py#L268-L314)).

| Schema mismatch | Behaviour |
|---|---|
| DB version > 50 (schema built by a newer HA) | recorder logs "The database schema version %s is newer than %s…" and stops; history/energy unavailable ([core.py L737-746](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/core.py#L737-L746)) |
| DB version < 50 | HA migrates on start (`Upgrading recorder db schema to version …`) ([migration.py L342-376](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/migration.py#L342-L376)) |
| Source and target built by different HA versions (B) | columns may differ, so COPY fails or values land in the wrong shape. Build the schema with 2025.9.4 and don't upgrade HA between snapshot and switch |

| Queue while blocked | events queue in memory. Past 65 000 events **and** with < 256 MiB RAM free, HA logs "The recorder backlog queue reached the maximum size…" and stops recording until restart | [core.py L362-395](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/core.py#L362-L395), [const.py L30-31](https://github.com/home-assistant/core/blob/2025.9.4/homeassistant/components/recorder/const.py#L30-L31) |

A CNPG switchover that completes within about 30 s (the default 10 × 3 s) should therefore lose nothing. This is inferred from the code and not measured. Raising `db_retry_wait` widens the window. psycopg2 sets no connect timeout of its own. Adding libpq's `?connect_timeout=10` to `db_url` would bound a hung TCP connect; that is a suggestion and not verified against HA.

## 6. Recommendation

**B.** Reasons, in order:

1. **It keeps only what must survive.** Short-term history is expendable per the ticket, and A's extra payload (8 days of `states`/`events`) is exactly the part with the failure reports: legacy columns, FK order, bytea, timezone.
2. **It takes HA's own "new DB" path** (`initial_schema_version = 50`), so no data migrator runs over imported rows. A instead inherits the SQLite DB's `schema_changes`/`migration_changes` history, which is where post 21 broke.
3. **Three tables, three identity sequences, one FK edge.** All three are checkable by row count before the restart.

A stays a fallback if history is wanted. Use the same pre-created schema, the load file above and the sequence fix. ha-db-universal-migrator automates A (schema from models, COPY, sequence reset, count check), but it is two months old, has 6 stars and no CI, and assumes HA is stopped. Run against the `.backup` copy via `SRC_DB_URL`, it would not need HA stopped; that is unverified.

## Not confirmed from a primary source

- That pgloader `data only` needs no CAST clause for v50, and that it orders tables to satisfy FKs. Both are derived from the source, not from a posted run.
- How `sqlite3 .backup` behaves against HA's live WAL writes. The CLI copies 100 pages per step with no sleep ([shell.c.in L10738](https://github.com/sqlite/sqlite/blob/master/src/shell.c.in#L10738)), and the backup API restarts when another connection writes ([backup.html](https://www.sqlite.org/backup.html)). With commits every 5 s a 600 MB copy may restart. `VACUUM INTO` is a single-transaction alternative.
- The gap behaviour in §3 (energy for the gap booked to the first period after the switch). Read from code, not tested.
- The CNPG default encoding (docs unreachable), and the exact psycopg2 version in the 2025.9.4 image.
- Whether a bare `create_all` is byte-identical to the schema HA builds on its own first start. The code path is the same, but `pre_migrate_schema` and `_initialize_database` add only rows, not DDL, for a new DB.
